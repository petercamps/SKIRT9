# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SKIRT is a Monte Carlo radiative transfer C++ code for dusty astrophysical systems (`SKIRT/`). It's built on top of SMILE (`SMILE/`), a generic, SKIRT-independent framework for declaring a class hierarchy's properties via metadata and auto-deriving a schema from it — used both to parse/write `.ski` parameter files and to drive `MakeUp` (`MakeUp/`), the Qt desktop Q&A wizard for building `.ski` files interactively. All three share the same schema, so the CLI parser and the wizard enforce identical rules.

## Build

The build lives in a sibling directory `../release` (i.e. next to `git/`, not inside it). From the repo root:

```bash
./configSKIRT.sh              # configure the cmake build (only needed once, or after changing build options)
./makeSKIRT.sh <threads>      # build, e.g. ./makeSKIRT.sh 8
```

`makeSKIRT.sh` builds the `skirt` CLI (`release/SKIRT/main/skirt`) and, if enabled, `MakeUp.app`. When `BUILD_MAKE_UP` is enabled, building MakeUp also regenerates the SMILE schema file (`release/MakeUp/schemas/skirt.smile`) by running `skirt -x` — a malformed SMILE conditional-value-expression (e.g. in an `ATTRIBUTE_TYPE_INSERT`/`ATTRIBUTE_INSERT`/`ATTRIBUTE_TYPE_ALLOWED_IF` string) surfaces as a build failure at that step, so with MakeUp enabled a clean build is a reasonable sanity check for schema-metadata edits, not just C++ changes. Without MakeUp, running `skirt -x` by hand performs the same check; it writes `skirt.smile` to the current directory.

To adjust a build option: `./configSKIRT.sh <OPTION_NAME>=<value>`. Relevant options (see top-level `CMakeLists.txt`, `SKIRT/mpi/CMakeLists.txt`, `SKIRT/h5/CMakeLists.txt`): `BUILD_MAKE_UP` (requires Qt5/Qt6), `BUILD_WITH_MPI`, `BUILD_HDF5` (requires the HDF5 C library, see below), `BUILD_WITH_LTO` (on by default, see below), `WARNINGS_AS_ERRORS` (CI builds with this on), `BUILD_DOX_STYLE`. SMILE-only options `BUILD_SMILE_TOOL`/`BUILD_SMILE_SHAPES` build small standalone SMILE example/console tools.

`BUILD_WITH_LTO` (top-level `CMakeLists.txt`, default `ON`) enables link-time optimization through CMake's `INTERPROCEDURAL_OPTIMIZATION` for the `Release` build type of every target. It is skipped, with a status line in the configure output, when CMake's `check_ipo_supported` probe fails (e.g. Clang on Linux without `llvm-ar`) and for GCC on macOS (see the comment in `CMakeLists.txt`). LTO inlines across `.cpp` files, so compare performance only between builds with the same setting. Each link reruns the LTO backend, making incremental rebuilds slower (about 7 s locally); use `./configSKIRT.sh BUILD_WITH_LTO=OFF` for a build tree meant for quick edit-build cycles. Avoid a `thread_local` static data member of a class template (or any other `thread_local` variable of a template) that needs dynamic initialization: ThinLTO with Apple's linker discarded the separate initialization function of such a member while code inlined into another translation unit still referred to it, which failed the link. Use a function-local `thread_local` instead, as `ThreadLocalMember` (`SKIRT/utils`) does.

`BUILD_HDF5` (`SKIRT/h5/CMakeLists.txt`, default `OFF`) adds support for reading input files from an HDF5 file and writing output files to one (see "Input and output files and HDF5 bundles" below). It requires the HDF5 C library on the system (`brew install hdf5`, `apt install libhdf5-dev`, ...), located through `find_package(HDF5)`; SKIRT uses the C library only, not HDF5's own C++ layer. With the option off, the same code compiles against a stub and nothing depends on HDF5: a run that needs an HDF5 file then ends with a fatal error saying so. Any change to the `h5` target or its clients must therefore build both ways — a second build tree configured with the other setting is the quickest check. On Windows, where HDF5 typically comes from vcpkg, CMake also needs the vcpkg toolchain file and target triplet (`-DCMAKE_TOOLCHAIN_FILE=<vcpkg>/scripts/buildsystems/vcpkg.cmake -DVCPKG_TARGET_TRIPLET=<triplet>`), which also copies the HDF5 DLLs next to the executables.

Simulation resource files (dust properties, SED libraries, etc.) are not checked into the repo; `./downloadResources.sh` fetches them into a sibling `resources` directory next to `release`.

## Formatting

```bash
./formatSourceCode.sh
```

Requires clang-format **version 18.1** exactly (looks for `clang-format-18` then `clang-format` on `PATH`; refuses to run against any other version — CI uses `clang-format-18` on Ubuntu 24.04 and fails the build on any diff). Only `.hpp`/`.cpp` are reformatted (not `.h`/`.c`/`.cc`, to leave vendored third-party code alone).

## Typical edit workflow

1. Make the code change.
2. `./makeSKIRT.sh <threads>` — confirm it builds cleanly.
3. `./formatSourceCode.sh` — confirm clang-format needed no changes (or accept the ones it makes).
4. Re-run `./makeSKIRT.sh <threads>` if formatting changed anything, to reconfirm.
5. `git diff` / `git status` to review before committing.

## Standing orders

These apply to any change to this repository — including when reviewing a pull request, not just interactive work in a single session.

- **No cyclic dependencies between `SKIRT/` targets.** Every `SKIRT/` subdirectory is its own CMake target, organized as a strict dependency tree (see Repository layout below) — nothing lower in the stack may depend on something higher, directly or transitively. If a proposed change would introduce a cycle, refuse it and flag the problem rather than working around it silently (e.g. by re-homing a header to break the cycle without saying so, or leaving a residual cross-target `#include` unaddressed).
- **Flag any new dependency between `SKIRT/` targets, even when it's topologically valid** (i.e. doesn't violate the ordering above). A change that adds a `#include` reaching into a different target's headers, or a new `target_link_libraries`/`include_directories` entry in a target's `CMakeLists.txt`, changes the shape of the dependency tree — surface this explicitly, whether writing or reviewing such a change, rather than letting it pass silently just because it stays within the allowed higher-depends-on-lower direction. New coupling between targets is an architectural decision worth a second look on its own, separate from whether it happens to introduce a cycle.
- **Flag any change outside `SKIRT/`** (e.g. in `SMILE/`, `MakeUp/`, or this file) before making or approving it, even when it's a small, obviously-correct fix. Changes inside `SKIRT/` need no special confirmation.
- **Keep `INCLUDE_PATH` in sync with the `SKIRT/` target list.** Both `Docs/doxygen/html.doxygen` (this repo) and `Web9/git/staging/doxygen_skirt.txt` (the sibling documentation repo) list every `SKIRT/<target>` directory in their (non-recursive) `INCLUDE_PATH`, so Doxygen can resolve cross-target `#include`s while expanding the `ItemInfo.hpp` property macros — see the comment above `INCLUDE_PATH` in either file for the full mechanism. Add, remove, or rename the corresponding entry in *both* files whenever the `SKIRT/` target list changes.
- **Guard divisions in binning or weighted-average code against a degenerate input.** A histogram bin index computed as `(x - min) / (max - min)`, or a weighted average as `Σ(w·v) / Σw`, breaks when every sampled value is identical (`max == min` — plausible for a symmetric or single-cell model) or nothing has weight (`Σw == 0`): both produce `0/0 = NaN`, which is undefined behavior once cast to an integer bin index, and otherwise silently zeroes out a downstream weighted sum (one `NaN` term poisons the whole sum, discarding every other valid contribution along with it). This exact shape of bug was found and fixed independently in half a dozen places across `SKIRT/medium` and `SKIRT/probe` during a full-codebase review (commits `71d7cac`, `20fdfbc` on branch `review`) — treat it as a demonstrated blind spot in this codebase, not a hypothetical one, when writing or reviewing similar code.
- **Flag deviations from the documented coding style when writing or reviewing new code.** `clang-format` (see Formatting above) enforces layout only; naming conventions and preprocessor/`using`/pointer/container/exception-handling conventions are documented separately in `root/text/33-DeveloperGuide/DevCoding.txt` (sibling `Web9/git` repo — see Documentation and project layout below). Check new code against it and call out departures explicitly, rather than letting them pass just because the code compiles and formats cleanly.
- **Check `SMILE/fundamentals/Basics.hpp` before adding an `#include` for a standard library header.** Every SKIRT and SMILE source file (excluding the vendored third-party code) includes `Basics.hpp`, directly or transitively. It already includes the commonly used standard headers (e.g. `<algorithm>`, `<cmath>`, `<cstddef>`, `<cstdint>`, `<memory>`, `<string>`, `<tuple>`, `<utility>`, `<vector>`), and it brings `std::string`, `std::vector`, `std::size_t`, `std::min`, `std::max`, and `std::abs` into the global namespace. Don't add an `#include` for a header that `Basics.hpp` already provides.

## Running a simulation

```bash
release/SKIRT/main/skirt -o <output-dir> <path-to-ski-file>
```

The output directory must already exist (`skirt` will not create it). The input directory is given with `-i <dir>` (the current directory by default); in a build with HDF5 support it can be followed by an HDF5 file in that directory and a group in that file, as `-i <dir>/<hdf5file>:<suite>`, so that input files missing from the directory are read from that file instead. Likewise, the output directory can be followed by an HDF5 file and a suite, as `-o <dir>/<hdf5file>:<suite>`, so that the output files that support it are written as bundles in that file (created if needed), while all other output files, including the log file, are still written to the directory (see "Input and output files and HDF5 bundles" below). The `.ski` file is validated against the SMILE schema at parse time — this enforces the same `ATTRIBUTE_TYPE_ALLOWED_IF`/`ATTRIBUTE_RELEVANT_IF` metadata rules as the interactive wizard, so a schema-metadata bug can make an otherwise-valid `.ski` file unparseable (or vice versa, let through a combination the runtime then rejects) independently of the C++ runtime logic — when changing behavior that depends on item metadata, both layers may need updating (see Architecture below).

There is no in-repo unit test suite or `ctest` target. Correctness is checked with a separate functional/regression suite of 800+ `.ski` test cases with reference output (in a sibling `Functional10` directory on this `v10beta` branch, a copy of the SKIRT 9 suite in `Functional9` that is being updated for SKIRT 10; see below), run via the Python Toolkit for SKIRT (PTS): `pts test_fun <pattern>` (e.g. `pts test_fun *Disk*`) or `pts test_fun .` for the full suite, `pts endorse_fun <pattern>` to accept new reference output after verifying it. Neither directory is part of this repository. On this branch, never run or modify anything under `Functional9`: it holds the SKIRT 9 suite and must stay untouched. Under `Functional10`, Claude may run tests and add or modify test cases, but endorsing — replacing reference output in a `ref/` directory, whether through `pts endorse_fun` or otherwise — requires the user's explicit confirmation, given only after Claude has presented the changed test cases, the nature of the differences, and an explanation; a confirmation covers only the test cases it was given for.

### Ad hoc test cases while developing a new feature

`Functional10/NEWTESTS/<CaseName>/` is a lightweight, manual staging area for trying out new `.ski` cases while a feature is still under development, before they're ready to become part of the official suite. Convention used for these cases:

- One case per subdirectory, named descriptively (e.g. `Functional10/NEWTESTS/FileFreqUnits/`), containing a single `.ski` file plus `in/`, `out/` and `ref/` subfolders — mirroring the PTS layout so a case can later be relocated into the real suite with no restructuring.
- Any input file the ski file references (e.g. for a `File...`-style class) goes in `in/`.
- Run `skirt` directly (not `pts test_fun`), single-threaded, with input/output isolated to that case's own folders:
  ```bash
  release/SKIRT/main/skirt -t 1 -i Functional10/NEWTESTS/<CaseName>/in -o Functional10/NEWTESTS/<CaseName>/out Functional10/NEWTESTS/<CaseName>/<name>.ski
  ```
- A case that needs another value for the `-i` or `-o` option than its `in/` or `out/` folder — an HDF5 file in that folder, possibly with a suite — states it in a text file `command_line.txt` in the case directory, on a line `-i <value>` or `-o <value>` with the value relative to the case directory (e.g. `-i in/data.hdf5:run1` or `-o out/data.hdf5:run1`); use that value when running `skirt` directly. The functional test procedure of PTS reads the same file, taking the input path from the first line starting with `-i` and the output path from the first line starting with `-o`, and ignoring other lines. The output path must refer to `out/` or to an HDF5 file in it, because the procedure compares the plain files in `out/` with those in `ref/`. For an HDF5 file, the procedure first converts the bundles at that location to plain files in `out/` (as `pts convert_from_hdf5` does), and compares each converted file according to the type of its bundle rather than byte for byte, since the conversion does not reproduce SKIRT's number formatting: column text files to the nine significant digits that SKIRT writes, spatial grid plot files by their polylines to eight significant digits, and FITS files by their content (pixels as 32-bit floats, units, axes, and observer information); a file written both as a plain file and as a bundle makes the case fail, except for the log and parameter files, and for a column text file whose bundle holds the same information as the plain file (SKIRT writes such files, like those of the `HistoryProbe`, incrementally and also stores them as bundles at the end of the run).
- Leave `ref/` empty while the case is in `NEWTESTS`. Promoting `out/` into `ref/` is endorsing, and moving a finished case out of `NEWTESTS` into its permanent location adds it to the official suite; both require the user's explicit confirmation, as for endorsing above.
- For testing an SED (or another similarly self-contained item), a minimal `NoMedium` simulation with one `PointSource` and one or more `SEDInstrument`s is enough; no medium system is needed. When a feature has multiple independent parts worth checking at different resolutions (e.g. several emission lines), give it several `SEDInstrument`s in one ski file rather than several ski files: one coarse instrument spanning the full range (using the system's `defaultWavelengthGrid`) to confirm the spectrum is ~0 away from the features under test, plus one tightly-zoomed instrument per feature, each overriding the default with its own `<wavelengthGrid>` element.
- For a quick visual sanity check, a temporary plotting script (e.g. Python/matplotlib reading the `*_sed.dat` output) is fine, but keep the script and its images entirely out of `Functional10` — use the scratchpad instead — and delete them once reviewed, since they aren't part of the test deliverable.

## Architecture

### Repository layout

- `SKIRT/` holds one CMake target per subdirectory — flat, no nested grouping directory, and no cross-target cycles. Each target's own `CMakeLists.txt` header comment documents exactly what it contains; from the bottom of the dependency stack up: `utils` (plain non-`SimulationItem` math/geometry helpers: `Box`, `Direction`, `Position`, `PhotonPacket`, `Quadrics`, `PathSegmentGenerator`, ...), `mpi` (MPI support, or a single-process stub if built without it), and `h5` (a thin C++ wrapper around the HDF5 C library, or a stub if built without it) depend on nothing but SMILE; `tools` (the `SimulationItem` base class itself, logging, random numbers, unit systems, the parallel execution engine, stored-table/text/FITS I/O) sits above those; then one target per class-hierarchy domain — `geometry`, `sed`, `wavelength`, `field`, `grain`, `source`, `material`, `medium`, `instrument`, `probe`; and `simulation` at the top (`MonteCarloSimulation`, `Simulation`, `ConfigurationSetup`, `SimulationItemRegistry`, plus the CLI entry point `SkirtMain`/`SkirtCommandLineHandler`), which also builds the `skirt` executable itself — deliberately placed at `release/SKIRT/main/skirt` rather than `release/SKIRT/simulation/skirt`, for backward compatibility with external procedures that hardcode that path.
- `SKIRT/fitsio`, `SKIRT/tetgen`, `SKIRT/voro` — vendored third-party libraries (CFITSIO, TetGen, Voro++).
- `SMILE/schema` — the `ItemInfo`/`NameManager`/`PropertyHandler`/`SchemaDef` metadata engine (see below).
- `SMILE/serialize` — reads/writes SMILE data sets to/from XML (i.e. `.ski` files).
- `SMILE/wizard` — the Q&A engine `MakeUp` is built on.
- `SMILE/fundamentals` — low-level shared utilities (e.g. `BooleanExpression`, used to evaluate the conditional-expression attributes below).

### The SimulationItem / SMILE metadata system

This pattern spans nearly the whole codebase and matters for adding or modifying almost any class.

- Every configurable class derives (directly or indirectly) from `SimulationItem` (itself derived from SMILE's `Item`) and declares its shape via macros from `SMILE/schema/ItemInfo.hpp`: `ITEM_CONCRETE`/`ITEM_ABSTRACT` for the class itself, `PROPERTY_*` for each discoverable property, `ATTRIBUTE_*` for metadata on the class or the most-recently-declared property (default values, min/max, visibility/relevance conditions, etc.). These macros generate the private data member, public getter, and private SMILE-only setter for each property, plus the metadata used to derive the SMILE schema.
- Conditional attributes (`ATTRIBUTE_RELEVANT_IF`, `ATTRIBUTE_DISPLAYED_IF`, `ATTRIBUTE_TYPE_ALLOWED_IF`, ...) are boolean expressions evaluated against a `NameManager` (`SMILE/schema/NameManager.*`) that accumulates named flags while walking the item tree in property-declaration order: **uppercase** names are global (persist for the whole configuration session, e.g. `"Emission"`, `"IteratePrimary"`, `"RadiationField"`), **lowercase** names are local (scoped to the current item, discarded when its subtree finishes). `ATTRIBUTE_INSERT`/`ATTRIBUTE_TYPE_INSERT` are how a class or property contributes new flags into these sets. This is how, e.g., choosing a `DustEmission` simulation mode changes which options are later offered or which defaults apply — both in the wizard and when parsing a `.ski` file, since both use the exact same schema evaluation.
- This flag mechanism is one-way (flags only ever get added, never removed) and strictly ordered by property declaration — a global flag set by one branch of the tree (e.g. while processing `sourceSystem`) is visible to everything processed afterward (e.g. `mediumSystem`, since it's declared later), but there's no way to later isolate "which branch contributed this flag." Distinguishing per-branch contributions (as needed e.g. for the per-source vs. per-medium symmetry tracking below) requires an explicit marker flag inserted at the boundary between branches, not something the mechanism gives you for free.
- The `ITEM_CONCRETE` macro defines an inline default constructor, which must be able to destroy the data members if an exception occurs. A `std::unique_ptr` data member of an item therefore needs the complete type of its target in the item's header, even if the item's destructor is defined out of line; a forward declaration does not suffice.
- **Every new `SimulationItem` subclass must be registered** in `SKIRT/simulation/SimulationItemRegistry.cpp`: add its header `#include` (alphabetized) and an `ItemRegistry::add<YourClass>()` call in `SimulationItemRegistry::SimulationItemRegistry()` (registration order there is the order it appears in the wizard's choice lists). A class that compiles but isn't registered is invisible to both the parser and the wizard.

### Top-level simulation structure

A `MonteCarloSimulation` (`SKIRT/simulation/MonteCarloSimulation.*`) is the root of the runtime object hierarchy. It holds four "system" compartments, each its own `SimulationItem` subtree and each the namesake of its own target: `SourceSystem` (`SKIRT/source/`, primary emitting sources), `MediumSystem` (`SKIRT/medium/`, transfer media, the spatial grid, and radiation-field storage), `InstrumentSystem` (`SKIRT/instrument/`), and `ProbeSystem` (`SKIRT/probe/`). It also owns a non-discoverable `Configuration` instance, set up very early in the process, that other items query during their own setup for cross-cutting derived state (which simulation phases are active, dimension/symmetry requirements, wavelength grids, ...) rather than reaching across the hierarchy directly — split into an abstract base holding the trivial inline getters (`SKIRT/tools/Configuration.*`) and a concrete `ConfigurationSetup` holding the setup-time logic that computes them (`SKIRT/simulation/ConfigurationSetup.*`).

Setup runs depth-first: `SimulationItem::setup()` calls `setupSelfBefore()`, recurses `setup()` into children, then calls `setupSelfAfter()` — the before/after split exists because some state can only be computed correctly before vs. after children have configured themselves (and `setupSelfAfter()` is generally where cross-item queries and logging happen).

During the photon life cycle, `PhotonPacket::getScatteringInfo(int h)` (`SKIRT/utils/PhotonPacket.*`) returns a pointer into a per-packet vector of cached per-medium-component scattering state, keyed by component index `h`. Repeated calls for the same `h` are safe (they return the existing entry via linear search), but a call for a *different*, not-yet-cached `h` can grow the underlying vector and invalidate any pointer a caller is still holding from an earlier call. The `MaterialMix` scattering-helper classes that get handed a live photon packet during scattering (`ComptonPhaseFunction`, `DipolePhaseFunction`, `XRayAtomicGasMix`'s internal `ScatteringHelper` hierarchy, and similar delegates in `SKIRT/material`) avoid this hazard by construction: their public interfaces accept only `StokesVector*`/`const StokesVector*`, never a photon packet, so they cannot themselves trigger a re-entrant `getScatteringInfo()` call that would invalidate a pointer their caller is holding. This includes `const PhotonPacket*`: the records are a `mutable` cache of values drawn for the current scattering event, and `getScatteringInfo()` is a `const` function, so that a peel-off function can fill them through the constant packet it receives (without a `const_cast`). A new `MaterialMix` that caches a `ScatteringInfo*` across a call into a delegate accepting a photon packet, const or not, would need to either avoid that pattern or re-fetch the pointer afterward.

### Material mixes and the medium state

The medium state (`SKIRT/material/MediumState.*`) holds, for each spatial cell, the common variables (volume, bulk velocity, magnetic field) and, for each medium component, the number density followed by the custom variables of its material mix, stored contiguously. A material mix declares its custom variables once, during setup (`setupSelfBefore()`, or `setupSelfAfter()` when they depend on its children, as for a decorator), by adding them to a `StateVariableList` data member, which assigns consecutive custom indices and hands out a `StateScalar` or `StateArray` handle for each variable; `specificStateVariableInfo()` returns a reference to that list, so it may be called only after the mix has been set up. The mix reads and writes its variables through the handles (`_temperature(state)`, `_temperature(state) = T`, `auto kappa = _opacityExt(state); kappa[k]`), which yield a value or a read-only `Span` (`SMILE/fundamentals/Span.hpp`) for a constant state, so that an opacity function never needs to cast away constness; `custom(i)` and `setCustom(i, value)` remain for code that works with indices, such as the probes and the `DustDestructionRecipe`. A custom variable can have a short name (letters, digits, and underscores, unique within the mix), by which other code finds it (`specificStateVariableInfo().index("T")`, the `variables` property of the `CustomStateProbe`); the temperature and the metallicity are custom variables with the standard names `T` and `Z`, created by `StateVariable::temperature()` and `metallicity()`.

An imported medium imports exactly the quantities its material mix or family requests through `parameterInfo()`, including the temperature and the metallicity (requested first, in that order, by the mixes that use them), each with a kind (`QuantityKind`: intensive quantities are averaged over overlapping entities and samples, categorical ones taken from the entity with the largest weight). The columns of an import file are the geometry, the mass or density, the velocity and magnetic field if configured, and then these quantities; every requested quantity must be present, since the defaults of a mix apply to a geometric medium only, and the dust mass is no longer derived from a metallicity or a maximum temperature. A family is configured through the same `materialMix` property, of base type `MaterialMixProvider` (the common base of `MaterialMix` and `MaterialMixFamily`, which also defines the `Capabilities` structure that describes a mix, or all members of a family, without constructing one). A family also declares through `hasUniformMass()` whether all its members have the same mass per entity (true for the `XRayIonicGasMixFamily`, whose members all have the proton mass; false by default, including for the `SelectDustMixFamily`); only then does an imported medium convert between mass and number densities with its representative mix, and a particle medium offer the exact mass in a box (`MassInBoxInterface`) to the tree policies and the cell densities, which otherwise fall back to sampled densities. The medium system verifies the declared uniform mass for each member it uses.

A material mix with a dynamic medium state can opt in to a staged update (`hasStagedStateUpdate()`, also a member of `Capabilities`): stage 1 (`prepareSpecificStateUpdate()`) runs for each cell in parallel; after a synchronization of the state between processes, stage 2 (`beginSpecificStateUpdate()`) runs once on each process, serially, with read access to the complete `MediumState`; stage 3 is the per-cell `updateSpecificState()`; and after the next synchronization, stage 4 (`endSpecificStateUpdate()`) runs once on each process. Data shared between stages 2 and 3 live in `mutable` members of the mix for one update only, and all processes must arrive at identical data in stage 2: a calculation that stage 2 distributes over processes must be combined with the `ProcessManager`, which fails with an MPI error if the processes disagree on the size of the data, but not if they merely disagree on its contents. The test-only `TrivialStagedGasMix` illustrates the protocol.

Convergence criteria keep their history in the `IterationHistory` (`SKIRT/tools`), a non-configurable child of the simulation found with `find<IterationHistory>()`, rather than in `mutable` members: a scalar series is keyed on a simulation item and an id chosen by the client, has loop, grid, or simulation lifetime, and advances one slot per iteration (the iteration loops call `beginLoop()` and `beginIteration()`), and a cell window holds per-cell running sums for dynamic grid refinement. A material mix marks state variables for aggregation (`StateVariable::aggregated(id)`), and the medium system records their volume integrals in aggregate series after setup and after each state update; `isSpecificStateConverged()` receives a `HistoryScope` bound to the medium component, through which the mix reads its aggregates and keeps further series. A recorded value must be identical on all processes. The `HistoryProbe` writes all scalar series to a file per iteration loop. It takes its columns from the series that exist in the first iteration of the loop, so a series must be declared in that iteration, even if it receives values only later.

### Dust emission: exact absorption and the self-heating rebalance

In a simulation with dust emission and at least one dust medium, the medium system accumulates the luminosity absorbed by dust in each cell along the photon packet paths, with the dust opacity at each packet's exact (perceived) wavelength, in the arrays `_labs1` (primary), `_labs2` (stable secondary), and `_labs2c` (secondary being accumulated). They follow the life cycle of the radiation field tables `_rf1`, `_rf2`, and `_rf2c`: `MediumSystem::storeRadiationField(primary, pp)` fills both in one loop over the path segments (the dust opacity comes from the private helper `DustAbsorptionOpacity`, with cross sections per dust component obtained once per path if `Configuration::hasConstantDustAbsorptionSections()`), `communicateRadiationField()` sums them over processes, and `clearRadiationField(true)` clears only the primary table and array, so that the stable secondary field persists across merged iterations. `dustLuminosity(m)` and `totalDustAbsorbedLuminosity()` return the exact values, which normalize the dust emission; the binned radiation field still sets the shape of the emission spectrum (mean intensity, dust temperatures, cell libraries) and feeds the radiation field probes. Absorption at wavelengths outside the radiation field wavelength grid is counted as well, and its fraction is reported after each emission segment, as a warning above 1%.

If the simulation iterates over secondary emission and dust emission is the only secondary emission, the medium system owns a `SelfHeatingRebalancer` (`SKIRT/medium`, not a simulation item), unless the `rebalanceSecondaryEmission` option of `DustEmissionOptions` is off. The secondary and merged loops of `MonteCarloSimulation` call `MediumSystem::beginRebalance()` before launching the secondary packets of every iteration, and `endRebalance()` after communicating the secondary field. The rebalancer partitions the cells into regions (weighted quantiles of the ratio of absorbed secondary to primary luminosity and of the absorbed luminosity per unit dust mass), tallies the luminosity launched from each region, absorbed in each other region, and escaping, in per-thread objects (`ThreadLocalMember`) reached through a `Tally` handle that `storeRadiationField()` obtains once per path, solves the small linear system for the self-consistent emission of each region, and returns a factor per cell, by which the medium system rescales `_rf2` and `_labs2`. In the first iteration of a loop the stable secondary field is still zero, so nothing is rebalanced, but the rebalancer declares its history series anyway (see the `HistoryProbe` above). A dust-emitted photon packet carries its emission cell (`PhotonPacket::emissionCell()`, set by `DustSecondarySource::launch()` and reset to -1 by `launch()` and by `setEmulatedSecondaryOrigin()`), through which the tallies attribute its luminosity. Convergence (`MonteCarloSimulation::isDustEmissionConverged()`) requires either an absorbed secondary luminosity below `maxFractionOfPrimary` of the absorbed primary luminosity, or, from iteration max(w + 1, 3) on, with w = `numConvergenceIterations`, a mean luminosity deficit (the relative shortfall of the escaping dust luminosity with respect to the absorbed primary luminosity; evaluated only if dust emission is the only secondary emission) of at most `maxLuminosityDeficit` and a mean change of the absorbed secondary luminosity, excluding the first iteration of the loop, of at most `maxSecondaryChange`.

### Input and output files and HDF5 bundles

An input file named in a ski file (or fabricated by the program) can be provided as a regular file in the input directory or, in a build with HDF5 support, as a *bundle* in an HDF5 file: an HDF5 group holding one or more datasets with names fixed by a small data model per file type (for a FITS file, a dataset `data`). A *suite* is a group holding a set of bundles, e.g. the input for one simulation. Output files can likewise be written as bundles, in the HDF5 file and suite given with the `-o` option. Three layers implement this:

- **`SKIRT/h5`** wraps the HDF5 C library. `H5Lib` offers the only entry points that name a file (`openSuite()`, `openBundle()`, the existence test `hasBundle()`, and `createBundle()` for writing, each taking a path of the form `<filepath>:<suite>/<bundle>`); the first two hand out move-only `H5SuiteR`/`H5BundleR`/`H5DatasetR` objects (common base `H5ObjectR`) that release their resource on destruction and stay valid after their parent is gone. Attributes and dataset contents are returned in the type named by the function called (`getIntAttribute()`, `readDouble()`, ...), regardless of how they are stored, and a stored value that cannot be converted without loss is a fatal error. `createBundle()` creates the HDF5 file if needed, replaces an existing bundle with the same name (leaving the rest of the file untouched), sets the standard attributes `producer` (from `H5Lib::setProducer()`, called by the command line handler), `format`, and `created`, and hands out an `H5BundleW` whose functions create `H5DatasetW` datasets (common base `H5ObjectW`); values are written in the type named by the function called (`setIntAttribute()`, `createDoubleDataset()`, ...), with strings as variable-length UTF-8 and Booleans as the enumeration used by h5py. HDF5 allows a single writer only: a file that is open for reading, in this or another process, cannot be opened for writing. The internal namespace `H5Core` is the only place that includes the HDF5 headers, calls the library (under a single mutex, since the installed library may not be thread-safe), and contains the `BUILD_HDF5` conditional compilation; nothing else in the code may do any of these, and the headers of the target stay free of conditionals. The target is named `h5` rather than `hdf5` because a CMake target called `hdf5` collides with the one exported by the HDF5 library itself.
- **`FilePaths::input(name)`** (`SKIRT/tools`) does the name resolution, without any I/O. It returns two candidate locations: a regular file relative to the input directory, and a bundle in the HDF5 file and suite given with the `-i` option, if any. A name that itself embeds `<hdf5file>:<suite>/<bundle>` resolves to that bundle only, regardless of `-i`. An HDF5 file is recognized by its `.hdf5` extension followed by a colon (or ending the `-i` value). Because `StringUtils::isAbsolutePath()` treats any path containing a colon as absolute, code that handles such paths must use `FilePaths::isAbsolutePath()` instead. `FilePaths::output(name)` likewise returns the two candidate locations of an output file: a regular file in the output directory, and a bundle in the HDF5 file and suite given with the `-o` option, if any; `FilePaths::directoryPath()` returns the directory part of an `-i` or `-o` value.
- **Reader classes per file type** apply the rule "regular file first, bundle only if that file does not exist": `FITSInOutFile::read()` for FITS input (dataset `data`, the same name as in the bundle for FITS output, so that an output bundle can be read as input); `ColumnInFile` for column text files (one dataset per column, with a `column` index attribute and an optional `unit` attribute), with its subclass `AdaptiveMeshInFile` for adaptive meshes (extra datasets `is_leaf` and `topology`); and `StoredTable::open()` with `resource = false` for stored tables (a dataset per axis and per quantity; the data is copied into memory owned by the table, since a bundle cannot be memory mapped). `ColumnInFile` opens nothing until the first row is read; it then holds a `TextInFile` for a regular file, or loads the needed datasets as whole columns. Both share the column bookkeeping (matching physical to logical columns, `useColumns`, unit conversion) through the helper class `InputColumns`, so a change there affects text files and bundles alike. Code that reads a user input file must use these classes; `TextInFile` on its own reads only resources and regular files. When an input file has two candidate locations and is found at neither, each reader reports both in a single fatal error, using `H5Lib::hasBundle()`; a new reader should do the same. Resource files never go through any of this. In a dataset name, a vertical bar stands for a forward slash in a column, axis, or quantity name; the `pts.hdf5` package in PTS writes all bundle types with these conventions.
- **Writer classes per file type** write a bundle if `FilePaths::output()` returns a bundle candidate, and a regular file otherwise; only the root process writes. So far this holds for three classes in `SKIRT/tools`. `ColumnOutFile` is used for every column text output file (SEDs, light curves and their statistics, probe tables): a dataset per column named for the column description by the dataset name rules of the data model (the same rules as `pts.hdf5.datasetNames()`), with `column` and `unit` attributes, and the bundle attribute `description`. It resolves the location when the first row is written, so that a regular file is still streamed row by row through a `TextOutFile`, byte-identical to the output of older versions, while a bundle is collected in memory and written at `close()`. A client must call `close()` explicitly, because only that function can report a failure to write a bundle as a fatal error; the destructor never throws, and merely logs such a failure. `ColumnOutFile::copyToBundle()` stores a finished regular column text file as a bundle, for files that must be written row by row during the run. `FITSInOutFile::write()` and `writeMap()` (the item-context write functions formerly in `FITSInOut`, whose basic functions are now private) write instrument frames, data cubes, spectral-time maps, and probe cuts and projections: a bundle holds `data` (64-bit values, where a FITS file holds 32-bit ones) and the axis grids `x`, `y`, and `z` (for a regular axis, the pixel centers that the CRPIX/CRVAL/CDELT cards describe), each with a `unit` attribute, plus the bundle attributes `description` and, for a distant instrument, the observer information; a cube with a single frame has 2D `data` and a single `z` value. `SpatialGridPlotFile` writes the grid plots: every drawing function converts its coordinates to output units and calls the private `moveTo()`/`lineTo()`, which either stream to a regular file (byte-identical to older versions) or collect the datasets `points` and `moveto` (with a `unit` attribute) for a bundle; like `ColumnOutFile`, it needs an explicit `close()`. The tree topology of the `TreeSpatialGridTopologyProbe` is written through `ColumnOutFile` as a single integer column, with a column information line that files written by older versions lack; `TopologyTreePolicy` reads both forms, and the bundle. `TextOutFile` takes an optional text type: with a type and an HDF5 output path, it collects the text and writes an unstructured text file bundle (a scalar `text` dataset and a `type` attribute) at an explicit `close()`; the convergence report and the grain population tables are written this way (type `free form`), so that they become bundles only. The log file and the parameter file always remain regular files in the output directory; with an HDF5 output path, the command line handler also stores them as bundles (types `log` and `XML`) at the end of each simulation, and after a fatal error during the run, through `TextOutFile::copyToBundle()`. That function logs no message, because PTS recognizes a finished simulation by the "Finished simulation" message at the end of the log file; nothing may be logged after it.

**I/O cutover.** Every simulation reads all of its input during setup and writes all of its output after setup; the moment in between, after the `wait("setup")` barrier in `MonteCarloSimulation::setupSimulation()`, is the I/O cutover, recorded by `FilePaths::cutOver()`. Before it, bundles may be read but not written; after it, bundles may be written but not read (nor tested with `H5Lib::hasBundle()`); regular files are not affected. Every class that reads or writes bundles calls `FilePaths::verifyBundleInput()` or `verifyBundleOutput()` before each access, so a new reader or writer must do the same, and a new input file must be read during setup (in `setupSelfBefore()`/`setupSelfAfter()` or a function called from there), never when a probe runs or during the run, as `AtPositionsForm` illustrates. `cutOver()` also verifies that the process holds no open HDF5 objects (skipped when `-s` runs several simulations in the process, as flagged by `FilePaths::setSharedProcess()`) and lets the root process test-open the HDF5 output file, so that an unwritable output file is reported right after setup. Together with a single writer (the root process), this keeps the processes of an MPI run from violating the HDF5 concurrency rules. Within one process, `H5Core` makes a writer wait while another object holds the same file open for reading only (HDF5 cannot reopen such a file for writing), so that simulations run with `-s` may share an HDF5 file for input and output; the wait has a ten-minute limit, so a thread that holds a reader while it writes the same file gets a fatal error instead of a hang.

A change to these classes should be exercised in both build variants and with the functional test cases that read or write bundles, which derive from existing regular-file cases and must reproduce their output exactly (for the `H5Out*` cases in the `HDF5` category, which write bundles, after conversion by the PTS procedure).

### Symmetry ("dimension") bookkeeping

Both at runtime (`Configuration::sourceDimension()`/`mediaDimension()`/`gridDimension()`/`modelDimension()`) and in the SMILE schema (`SourceDimensionN`/`MediaDimensionN`/`RequiredDimensionN`/`DimensionN` flags inserted throughout the `Geometry`/`VectorField`/`Source`/`Medium` class hierarchies), the code tracks source and media symmetry separately: primary sources aren't discretized onto the spatial grid, so the grid's required dimension is normally just the media's, expanding to the combined source+media dimension only when the radiation field is actually stored. `Geometry`/`VectorField` (and their decorators) are shared between source and medium contexts, so their schema-level dimension contribution is tagged by whether `MediumSystem`'s `InMedia` marker has already been inserted (it always follows `SourceSystem`). See `SKIRT/simulation/ConfigurationSetup.cpp` and the `grid`/`samplingOptions` properties of `MediumSystem` for the current implementation.
